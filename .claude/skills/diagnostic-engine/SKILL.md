# 진단 문항 & 채점 설계

축을 측정 가능한 문항으로 바꾸고, 응답을 유형 코드로 환산한다. 산출물은 웹이 그대로 소비하는 **데이터 계약**이므로 스키마를 엄격히 지킨다.

## 1. 데이터 스키마

`references/data-schema.md`의 JSON 구조를 정확히 따른다. **반드시 먼저 읽어라.** 필드명·중첩을 바꾸면 웹이 깨진다.

## 2. 축당 3문항 (고정)

3문항이면 결과가 **3:0 또는 2:1**로 갈려 **동점이 발생하지 않는다.** 동점 처리 로직이 사라지고, 채점이 결정적이 된다.

- 2문항 → 1:1 동점이 생겨 임의 규칙(기본 극)이 필요해진다. 사용자는 왜 그 결과인지 알 수 없다.
- 4문항 이상 → 판별력은 거의 안 늘고 이탈만 는다.
- 3:0은 "뚜렷함", 2:1은 "약간 기울어짐"으로 결과에 표시한다.

## 3. 문항 작성 원칙

- **전문용어를 묻지 않는다.** "유치권 물건에 입찰하시겠습니까?"는 초보가 답할 수 없다. **상황과 금액으로 묘사**한다: *"낙찰받아도 이전 세입자 보증금 3,000만 원을 물어줘야 할 수 있습니다."*
- **선택지는 2개.** 4개면 고민이 길어지고 이탈한다.
- **유도 금지.** 한쪽이 명백히 옳게 들리면 안 된다. 두 선택지 모두 "그 값을 치르고 그 이득을 얻는" 형태여야 한다(싼 대신 위험 / 안전한 대신 비쌈).
- **한 축을 여러 각도로.** 같은 질문을 말만 바꿔 3번 묻지 않는다. 예 — 손품 축: 사람(명도) / 공사(수리) / 돈(예상 외 비용).

## 4. 사실 입력은 점수에 넣지 않는다

예산·지역·주택 보유 수·경험은 별도 `facts[]`로 받아 **검색조건 계산과 경고에만** 쓴다.

- **경험을 성향 점수에 넣지 말 것.** 경험은 성향이 아니다. 넣으면 초보는 영원히 안전형으로 나오고, 경험이 쌓여도 결과가 안 바뀐다. 대신 **안전장치**(초보 + 모험형 → 검색조건만 하향, 유형 코드는 유지)로 쓴다.
- **규제지역은 묻지 않는다.** 지역 입력에서 자동 판정한다. 초보는 답할 수 없는 질문이다. 판정 불가 시 보수적으로 계산하고 확인 안내를 띄운다.

## 5. 규제 경고 플래그

규제(대출제한·세금중과·규제지역)는 의사결정을 크게 바꾸므로 경고로 반영한다.

- **규제 수치는 절대 기억으로 쓰지 말고 `_workspace/00_regulations.md`만 근거로 한다.** 그 문서가 없으면 플래그를 만들지 말고 리더에게 알린다.
- 플래그는 `when`(조건) + `level`(danger/warn/info) + `title` + `message` 구조. 조건은 사실 입력과 축 코드의 조합으로만 쓴다.
- **신뢰도 전파**: grounding 문서가 `[불확실]`로 표기한 항목은 문구에 "확인 필요"를 포함한다. 단정하지 않는다.
- **경매 특수 플래그(중요)**: 경매 + 규제지역은 두 축으로 분리한다 — (1) 대출규제는 경매도 동일 적용(자금계획 경고), (2) 토지거래허가 실거주의무·자금조달계획서는 경매 면제(기회). `00_regulations.md` D절 근거.

## 6. 채점 알고리즘

1. 축마다 양극 점수를 합산한다(선택지 1개 = 1점).
2. 우세 극 코드를 채택한다. **축당 3문항이므로 동점은 없다.**
3. 축 순서대로 극 코드를 이어 붙인다(예: `A-SHP`). 접두는 `A-`.
4. 사실 입력 + 축 코드로 플래그를 평가한다.

채점 규칙은 `_workspace/02_scoring.md`로도 문서화한다 — 웹이 이걸 보고 JS를 구현하고, QA가 이걸로 재현 검증한다. 모호함 없이 결정적으로 쓴다.

## 7. 산출물

- `_workspace/02_scoring.md` — 채점 규칙 + 계산 예시 + **"점수에 넣지 않는 것"** 명시
